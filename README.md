**# Heart Disease Prediction and Decision Support System Using Machine Learning**

**## Overview**

This project is an intelligent heart disease prediction system developed using Machine Learning techniques.

The system analyzes a set of medical features related to a patient and uses a trained Machine Learning model to provide an initial prediction of the possibility of heart disease.

The system provides:

\- Disease prediction.

\- Probability of heart disease.

\- Risk level.

\- Web-based interface.

\- REST API for predictions.

\- Input validation.

\- Feature importance analysis.

\- Saved Machine Learning model.

\> Disclaimer: This project is intended for educational and research purposes only. The predictions generated by the system are statistical Machine Learning predictions and must not be considered a medical diagnosis or a replacement for professional medical advice.

**## 5. Data Preprocessing**

Several preprocessing steps were applied before training the Machine Learning models.

**### 5.1 Data Exploration**

The dataset was inspected to identify:

\- Number of rows and columns.

\- Data types.

\- Missing values.

\- Unique values.

\- Statistical properties.

\- Feature distributions.

**### 5.2 Missing Values**

Missing values were handled using appropriate strategies for numerical and categorical variables.

Numerical features were processed using median-based imputation, while categorical features were processed using the most frequent value.

**### 5.3 Removing the ID Feature**

The id column was removed because it represents a record identifier rather than a medical characteristic.

Keeping the ID could cause the model to learn patterns related to the record identifier instead of meaningful medical information.

**### 5.4 Target Variable**

A binary target variable named target was created.

The target represents:

\- 0 → No heart disease

\- 1 → Heart disease

\- 20% Testing Data.

The stratify parameter was used to maintain a similar class distribution between the training and testing datasets.

**### Numerical Features**

Numerical features were standardized using:

StandardScaler

**### Categorical Features**

Categorical features were converted into numerical representations using:

OneHotEncoder

Both preprocessing steps were integrated into a Scikit-learn Pipeline.

This ensures that the same preprocessing procedure is applied during model training and when making predictions on new patient data.

**## 9. Model Selection**

Random Forest achieved strong performance compared with the other evaluated models.

The model was then optimized using GridSearchCV.

Several hyperparameters were tested, including:

\- n\_estimators

\- max\_depth

\- min\_samples\_split

\- min\_samples\_leaf

The final Random Forest model was optimized using GridSearchCV after removing both the id and dataset fields.

The id field was removed because it is a record identifier rather than a medical characteristic. The dataset field was also excluded from the final model because it represents the source or collection group of the record rather than a direct patient medical characteristic.

The final deployed model therefore uses 13 patient-related input features and does not require id or dataset.

**---**

**## 10. Model Evaluation**

The final model was evaluated using an independent test set.

The following metrics were used:

**### Accuracy**

Measures the percentage of correctly classified samples.

**### Precision**

Measures how many of the samples predicted as positive were actually positive.

**### Recall**

Measures how effectively the model identifies positive cases.

Recall is particularly important in medical prediction problems because failing to identify a potentially affected patient can be significant.

**### F1-Score**

Provides a balance between Precision and Recall.

**### ROC-AUC**

Measures the model's ability to distinguish between the two classes across different classification thresholds.

**---**

**## 11. Final Model Results

The final model was evaluated on the independent test set after removing both `id` and `dataset`.

The final optimized Random Forest achieved:

| Metric | Score |
|---|---:|
| Accuracy | 0.8696 |
| Precision | 0.8482 |
| Recall | 0.9314 |
| F1-Score | 0.8879 |
| ROC-AUC | 0.9284 |

The optimized model showed strong recall, meaning that it identified a high proportion of positive heart disease cases in the test set.

The model was selected as the final model used by the Flask application.

The final model configuration was obtained using GridSearchCV and used:

- n_estimators = 100
- max_depth = 10
- min_samples_split = 5
- min_samples_leaf = 2

The final model does not use `id` or `dataset`.

## 16. Example API Response

An example response returned by the API is:

```json
{
    "prediction": 0,
    "probability": 0.369,
    "risk_level": "Medium",
    "diagnosis": "No high probability of heart disease",
    "patient_findings": [
        "Patient findings based on the entered medical features"
    ],
    "doctor_alerts": [
        "Doctor-oriented alerts based on the case"
    ],
    "recommendations": [
        "Case-specific recommendations and preventive guidance"
    ]
}
```

The response contains:

- `prediction`: The predicted class.
- `probability`: The predicted probability of heart disease.
- `risk_level`: The application-level risk category.
- `diagnosis`: A human-readable interpretation of the prediction.
- `patient_findings`: Findings generated from the entered patient features.
- `doctor_alerts`: Prioritized alerts intended to support clinical review.
- `recommendations`: Recommendations generated according to the combination of patient features and model risk.

The alerts and recommendations are intended as decision-support information and not as a substitute for professional medical evaluation.

## 17. Risk Levels**

The application converts the prediction probability into three risk levels:

\| Probability | Risk Level |

\|---|---|

\| Less than 30% | Low |

\| 30% to less than 70% | Medium |

\| 70% or higher | High |

These thresholds are application-level rules and are not clinically validated diagnostic thresholds.

**## 18. Input Validation**

The API includes an input validation system.

The system checks:

\- Required fields.

\- Unknown fields.

\- Categorical values.

\- Numerical values.

\- Numerical value ranges.

\- JSON request format.

For example, if the user sends:

age = -5

the API rejects the request before sending the data to the Machine Learning model.

The API returns a clear error message explaining the problem.

This helps prevent invalid input from reaching the prediction pipeline.

**## 28. Limitations**

Although the model achieved good performance on the test data, the project has several limitations:

\- The dataset is limited compared with real-world medical datasets.

\- The model depends on the characteristics of the training dataset.

- The final deployed model does not use the `dataset` source field as a prediction feature.

\- Performance may change when using data from different populations or healthcare systems.

\- The risk thresholds used by the application are not clinically validated.

\- The model does not replace professional medical evaluation.

\- The prediction probability should not be interpreted as a clinically validated individual risk score.

\- Machine Learning predictions should not be used as an independent basis for medical decisions.
